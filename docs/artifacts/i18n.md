# i18n

_Package group · packages/i18n_

**Content localization: one entry — one row per language**

i18n makes content types flagged `i18n: true` multilingual: **one row per locale**, with translation siblings tied together by a shared `locale_group_id`. The content library itself **does not know what a locale is** — all locale behaviour lives in this plugin and attaches to content through a single **synchronous open-host port**. The plugin owns no table and ships no migration: the set of locales is host configuration, and the `locale` / `locale_group_id` columns are added by content's own table builder.

- **2** packages in the group
- **4** HTTP routes
- **0** tables of its own
- **0** migrations
- **6** open-host port hooks
- **4** agent tools
- **9** admin slots
- **4** permission keys
- **3** virtual filter fields

## 01. Business description

i18n answers one product question: **how an editorial team runs the same material in several languages** without turning it into manual synchronization of copies. The plugin's answer is the “row per locale” model: the German version of an article is a separate entry with its own id, its own publication status and its own version history, but it belongs to the same **translation group** as the English one.

### The problem it solves

- **A translation is work, not a copy.** Each locale has its own draft, its own publication, its own revision feed. The German version can stay in draft while the English one is already live, and vice versa.
- **Shared fields are not translated twice.** The type's author marks a field as `localized` — that one varies by language. Everything else is **shared**: editing such a field in one locale rewrites it across all siblings within the same transaction. A product's price, an event's date, a slug — edited once.
- **A missing translation is visible.** The virtual filters `hasLocale` / `missingLocale` / `localeCount` in the records table and the “Translation coverage” card on the Insights page answer “where exactly are we behind” — by language and by content type.
- **The content library stays neutral.** content-server knows about the `locale` column only that it exists and is NOT NULL. What a “valid slug”, a “default locale” or a “fallback” is lives entirely here. Remove the plugin and types with `i18n: true` simply will not load (content-server's boot check says outright that a localization plugin is needed).
- **A language is markup, not a caption.** A locale's slug is contractually a BCP-47 tag, and the writing direction (`ltr`/`rtl`) is resolved by the server itself. So the admin UI sets `lang` and `dir` on field areas, on the locale's name and on previews without a lookup table of its own (WCAG 3.1.2 and 1.3.2).

### Who sees it

#### The translating editor

Opens an entry and, in the “Locale” panel, sees every configured language: the existing ones with their publication status, the missing ones with “Add”. Clicking a missing language opens a creation form already tied to the same translation group, carrying the source's shared fields.

#### The content manager

Switches the records table's language with one control, turns on the “Locales” column, filters for “no German”, and publishes or unpublishes every locale at once from the entry's menu.

#### The lead / product owner

The “Translation coverage” card on Insights: how many entries are fully localized, how many have not been started, how many are unfinished — broken down by language and by content type.

### What i18n is not

- **It is not text translation.** The plugin calls no translator whatsoever. The text is written by a human (or by the copilot through its propose tools); i18n is responsible for the structure and its integrity.
- **It is not interface localization.** The admin UI's own language is `react-intl` and the host's single `IntlProvider`. i18n localizes _content_, not button labels.
- **It is not the owner of the data.** Not one table, not one migration. The rows live in content's generated tables, and the locale configuration lives in the host's code.
- **It is not a separate write route.** Creating a translation is an ordinary `POST /api/content/:type` with a `localeGroupId` field. The plugin has no write endpoint of its own at all.

> **The key architectural idea**
>
> The layout is **layered but light** (ADR-0003): there is a `domain/` for value objects (`Locale`, `LocaleSet`) and pure policy (`LocalePolicy`), but **no** aggregate, unit of work or outbox — because there is nothing to write here, the plugin owns no tables. Instead, the defining feature is the **synchronous open-host port**: the extension must run _inside_ the content write's transaction, which is why a port, not an event, is the right integration.

## 02. Composition of the package group

The `packages/i18n` group is **two** packages. There is no separate `domain` package here (unlike `content` or `copilot`): the domain layer is small enough to live as a `src/lib/domain` folder inside the server package, while the admin package keeps its own small mirror of the rules.

| Package | npm name              | Role                                                                                                                 | What it owns                                                                                                                             |
| ------- | --------------------- | -------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| server  | @apograph/i18n-server | The NestJS plugin: binding content's port, the locale domain layer, 4 routes, the Insights read model, 4 agent tools | The locale registry, the fallback policy, shared-field synchronization, the virtual filters, the translation-group lock. **Zero tables** |
| admin   | @apograph/i18n-admin  | The admin plugin: **no routes and no menu items** — only contributions into other people's slots                     | 9 slots (8 of `content-admin`'s + 1 of `insights-admin`'s), 10 contributions, 4 data hooks, its own `domain/localePolicy`                |

### The server package's layout

| Folder                  | What is inside                                                                                                                                               | Framework-dependent |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------- |
| domain/value-objects    | `Locale` (slug format, non-empty name, direction), `LocaleSet` (non-emptiness, uniqueness, exactly one default, a ban on removing the default)               | no                  |
| domain/locale-policy.ts | `LocalePolicy`: `resolve`, `shouldWidenToDefault`, `fallbackChain`, `requiredLocalesForPublish`                                                              | no                  |
| domain/errors           | `InvalidLocaleError`, `InvalidLocaleSetError`, `UnknownLocaleError` — transport-neutral                                                                      | no                  |
| locales/services        | `LocaleRegistryService` — the only `@Injectable()` seam over the domain; `OrphanedLocaleChecker` — a boot-time reconciliation of the config against the data | Nest + Drizzle      |
| content/services        | `EntryLocaleExtensionService` (896 lines — the heart of the plugin), `LocaleGroupService` (group reads), `locale-group-lock.ts`                              | Nest + Drizzle      |

| copilot/                | Two read tools, two propose tools, two appliers                                                                                                              | Nest                |

> **Neighbours that are easy to confuse**
>
> **`@apograph/content-server`** declares the `CONTENT_ENTRY_EXTENSION` port, adds the `locale`/`locale_group_id` columns (on the type's `i18n: true` flag), owns the `relationLocaleSync` rule and writes revisions. **`@apograph/content-graphql`** serves `locale`, `localeGroupId` and `translations` — but it is an adapter over the same public-api. **`@apograph/transfer-*`** carries locales in the transfer document (`$locale`, `$localeGroup`). **`@apograph/insights-admin`** is the page i18n inserts its card into.

## 03. Roles and permissions

The plugin introduces **no permissions of its own**. It reuses four keys from Identity's content set — and that is deliberate: a locale is not a separate access object, it is a dimension of an entry. Whoever may read entries sees their locales; whoever may create entries may create a translation.

| Permission      | What it opens in i18n                                                                                 | Where it is checked                                                                                                                                 | admin | contributor | viewer |
| --------------- | ----------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | ----- | ----------- | ------ |
| content:read    | an entry's locale panel, the batch summary by group, the coverage card, both read tools for the agent | `GetEntryLocalesController`, `LocaleSummaryController`, `LocalizationCoverageController`, both `ToolDefinition.requires`                            | ✓     | ✓           | ✓      |
| content:create  | creating a translation (the “Add” row in the locale panel becomes clickable)                          | the front end only — `useHasPermission(CONTENT_CREATE)` in `LocaleWidget`; the server checks the permission on the `POST /api/content/:type` itself | ✓     | ✓           | —      |
| content:update  | both of the copilot's propose tools (`i18n_propose_translation`, `i18n_propose_bulk_translation`)     | `ToolDefinition.requires`; applying goes through `EntryWriterService.create` on the user's behalf                                                   | ✓     | ✓           | —      |
| content:publish | the “Publish all locales” / “Unpublish all locales” menu items                                        | the front end only — `useHasPermission` in both hooks; the operations themselves go through content's bulk endpoints, which guard the permission    | ✓     | ✓           | —      |

> **Why the permission for translating is content:update, not content:create**
>
> The copilot's tools require `content:update`, even though technically they create a row. The comment in the code explains: a translation is **a change to existing material**, not the appearance of something new, and that is exactly how an editor sees it. The batch (`i18n_propose_bulk_translation`) takes **the same** key — batching is a way to _ask_, not a way to obtain authority the single-item tool did not have (ADR-0005 §7).

### The three levels of route protection

All three content/insights routes carry the same trio: the session (the host's global `AuthGuard`) → `PermissionsGuard` with `@RequirePermissions(CONTENT_READ)` → `WorkspaceGuard` (the `X-Workspace-Id` header). The `GET /api/i18n/locales` route is the only one with no permission and no workspace: it serves the deployment's configuration, which is the same for everyone, and a session is enough.

The batch summary additionally carries `OriginGuard`, even though it is a read. The guard looks at **the verb the browser sees**: `POST` is the shape of any cross-site submission, the route is reachable with a cookie alone, and “it is only a read” is a property of today's handler that no test has pinned. For legitimate callers the guard is free (the admin UI sends an `Origin`, non-browser clients send nothing).

> **The type grant is not checked the same way everywhere**
>
> `resolveI18nType` (the HTTP path) **deliberately does not check** the workspace's content grants: its callers already stand behind a workspace-scoped controller they reached from our own UI. The agent's tools, on the other hand, **do re-check** the grants through `WorkspaceGrantsQuery.grantedSlugs`, because the type name arrives from the _model_, which can be steered by the content it read. “Not granted” and “does not exist” give the same message, so that a run cannot enumerate the deployment's types.

## 04. Data model — no tables of its own

This is the main fact about the package: `packages/i18n/server` has no `drizzle.config.ts` and no `migrations/` folder. There is nothing to own. Everything the plugin operates on lives in other people's objects.

| What                          | Where it physically lives                                                                                       | Who creates it                                                                                         |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| locale                        | a `text NOT NULL` column in the generated `content_<name>` table                                                | `content-server`, `buildTables()`, only when `meta.i18n`                                               |
| locale_group_id               | a `uuid NOT NULL DEFAULT gen_random_uuid()` column in the same place                                            | the same builder; the default is what makes **an ordinary entry creation start a new group by itself** |
| \<table>\_group_locale_unique | a unique index on `(locale_group_id, locale)`; on paranoid types a **partial** one (`WHERE deleted_at IS NULL`) | `content-server`. It is what makes a duplicate locale a clean 409 rather than a corrupted group        |
| (locale, \<field>\_id)        | the unique index for a one-to-one on an i18n type — “within one language a target is taken once”                | `content-server`: on a localized entry, “exactly one owner” must be counted in entries, not in rows    |
| locale_group_id               | a column in the revisions table                                                                                 | `content-server`, `revision-table.ts`                                                                  |
| the set of locales            | a literal array in `apps/server/apograph.config.ts` → `plugins.i18n.locales`                                       | the host. Not the database, not a settings table, not the UI                                           |

> **A consequence: “delete a locale” is a code edit, not an operation**
>
> Since the set of locales is a literal in the config, no delete operation exists. `LocaleSet.remove` is written and guards the default against deletion — but the plugin **never calls it**. There is only a diff nobody computes. Which is exactly why `OrphanedLocaleChecker` appeared (see section 12).

### The one lock the plugin does own

The advisory lock class `0x4c47` (“LG”) is the only “entity” i18n creates in the database. It is a transactional `pg_advisory_xact_lock(LG, hashtext(locale_group_id))` that serializes writes within one translation group. The class was chosen so as not to collide with the application's other locks: `WK` (a workspace's shared content), `RE` (revision numbering), `RL` (appending relations).

## 05. Locale policy

The first of the two main sections. “Locale policy” is the set of pure rules that determine **what a valid locale is**, **which locale counts as active** and **what it widens into**. The rules live in `domain/`, know nothing of Nest, Drizzle or React, and are covered by unit tests with no content scaffolding at all.

### What counts as a valid locale

The format rule belongs to the `Locale` value object (it used to be inline in the plugin factory). The `Locale.create` constructor rejects three things and throws `InvalidLocaleError`:

| Check       | Rule                                                                                                                | Examples                                                                                 |
| ----------- | ------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Slug format | `/^[a-z]{2,3}(-[a-z0-9]+)*$/` — a lowercase primary tag of 2–3 letters, then any number of hyphen-separated subtags | valid: `en`, `de`, `pt-br`, `zh-hans`, `az-arab`. Invalid: `EN`, `pt_BR`, `e`, `english` |
| Slug length | no longer than `LOCALE_SLUG_MAX_LENGTH = 35` — the practical BCP-47 bound                                           | —                                                                                        |
| Name        | `name.trim()` must not be empty                                                                                     | `{ slug: 'de', name: ' ' }` → an error                                                   |
| Direction   | `dir`, if given, is strictly `'ltr'` or `'rtl'`                                                                     | any other value → an error                                                               |

> **A slug is a BCP-47 tag, and that is a contract**
>
> The regex deliberately mirrors the lowercase form of BCP-47, and **nothing in the code upper-cases the region**. The reason is utilitarian: any `locale` value the plugin serves outward (in the locale list, in an `EntryLocaleItem`, in an entry's column) can be dropped verbatim into an HTML `lang` attribute. So the admin UI sets `lang={entry.locale}` on the field area, on previews and on the published page with no lookup table — and a screen reader stops reading German with English phonetics.

#### Writing direction is inferred, not asked for

`dir` is optional in the config and **always present on the wire**. If the host did not specify it, `inferLocaleDir(slug)` derives it from the slug by a three-step rule:

1. **An explicit script subtag decides first.** So `az-arab` is RTL and `ku-latn` is LTR, whatever the language is by itself.
   _RTL: adlm, arab, aran, hebr, nkoo, rohg, syrc, thaa, yezi · LTR: cyrl, latn, hans, hant_
2. **Otherwise the primary language subtag decides.** The list is deliberately short and conservative — these are the languages a CMS is actually configured with, not a mirror of CLDR. It only supplies a _default_.
   _ar, arc, ckb, dv, fa, he, ks, ku, nqo, ps, sd, ug, ur, yi_
3. **Otherwise — `ltr`.** So adding Arabic is one line of config rather than a silent accessibility failure.
   _a dir declared in the config always beats the inference_

### The invariants of a locale set

What a single locale cannot check is checked by `LocaleSet` (the `InvalidLocaleSetError` error):

- **Non-emptiness** — at least one locale.
- **Slug uniqueness** — a duplicate is rejected by slug name.
- **Exactly one default** — not zero and not two (`defaults.length !== 1`). This is what makes `LocaleSet.default()` a total function: it never returns `undefined`.
- **The config's order is preserved** — it is the display order in the switcher, in the panel, in the badges.
- **`remove()` refuses to delete the default** and refuses to delete a non-member. The method exists, but the plugin does not call it (see section 04).

The check is **early**: `I18nServerPlugin()` calls `assertConfig`, which is simply `LocaleSet.fromDefs(config.locales)`. A misconfigured host fails **at plugin construction** — before startup, before the first request.

### Which locale is active: the resolve rule

`LocalePolicy.resolve(slug?)` is the single gate every request-facing path goes through:

**slug absent** → **the default locale** · **slug configured** → **that locale** · **slug not configured** → **UnknownLocaleError → HTTP 400**

The domain throws a transport-neutral error; `LocaleRegistryService.resolve` — the only `@Injectable()` seam adapting the domain to DI — turns it into an HTTP 400. This is an important property: **an unknown slug never resolves to the default**. Silent substitution would mean a control labelled “English” while the list shows something else.

### The fallback chain

i18n has exactly one fallback and it is **short: the chain is at most 2 long**. There is no “pt-br → pt → en” hierarchy.

| `LocalePolicy` method                              | What it answers                                                  | Rule                                                                                                                                      |
| -------------------------------------------------- | ---------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| shouldWidenToDefault(requested, fallbackRequested) | whether the list should widen to the default locale              | `true` only when a fallback was requested **and** the requested locale is not itself the default (otherwise there is nowhere to widen to) |
| fallbackChain(requested, fallbackRequested)        | the ordered locales worth trying                                 | `[requested]` in strict mode, `[requested, default]` when widening                                                                        |
| requiredLocalesForPublish()                        | which locales must exist for a group to count as fully published | always `[default]` — a group cannot go live without its canonical translation                                                             |

**Two modes of reading a list**, and this is the only place a fallback is applied at all:

- **Strict** (the default, the records-table mode): `locale = X`. Untranslated groups are simply invisible. So an editor who switched to German sees German content rather than a mixture.
- **With widening** (`?localeFallback=default`, the relation-picker mode): “the requested locale **or** the group's default row where the requested row does not exist”. Implemented with an `OR` and a correlated `NOT EXISTS` against an alias of the same table. The guarantee is **one row per group**.

> **One rule, two implementations — and deliberately so**
>
> `LocalePolicy` is a _pure restatement_ of the same rule the SQL in `listScope` encodes. The adapter still renders the query itself; the domain does not render SQL. So the rule is written twice in the codebase: as a pure function (testable and readable) and as a Drizzle predicate (executable). ADR-0003 says outright that layering is **not obliged** to turn a correct open-host port into an event — and the same logic is extended here to the fallback.

### The client-side copy of the policy

The admin package has a `domain/localePolicy` — a framework-free mirror of the server rule (no React, no router), so that the switcher, the header chip and the editor widget resolve **one** rule rather than rewriting the same `??` chain three times.

| Function                                                   | What it does                                                                       | The subtlety                                                                                                                                                    |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| resolveActiveLocale({entryLocale, urlLocale, defaultSlug}) | the active locale by priority: the saved entry's locale → `?locale=` → the default | each source is checked **for emptiness**, not for nullishness: `?locale=` yields `''`, and a bare `??` chain would resolve the active locale to an empty string |
| findLocale(locales, slug)                                  | the configured locale for a slug, or `undefined`                                   | it does **not** substitute the default on a miss — the request will go out with the bad slug anyway, and the control must not label someone else's list         |
| isDefaultLocale / toLocaleListParam                        | the “default locale = a clean URL” rule                                            | the server scopes to the default when the parameter is absent, so the two spellings cannot diverge                                                              |
| localeName / localeDir                                     | the display name and direction for a slug                                          | `localeDir` is **a lookup, not a guess**: the admin UI keeps no list of RTL languages of its own                                                                |
| localeAttrs(locales, slug)                                 | the `{ lang, dir }` pair that gets spread onto an element                          | an unknown slug yields `{}` rather than the wrong language; an unloaded direction yields only `lang` rather than the wrong `dir`                                |

## 06. The synchronous open-host port

The second main section and the package's defining feature. All locale behaviour attaches to the content library through **one DI port**, called **synchronously, inside the same transaction** as the write itself.

### Who declares it and who binds it

The inversion here is not the usual one: **the port is declared by the consumer of the behaviour**, and bound by the provider.

1. **`content-server` declares the port.** The file contains only types and one `Symbol` — `CONTENT_ENTRY_EXTENSION`. It deliberately has no NestJS decorators: the implementations live in other packages.
   _packages/content/server/src/lib/extension/entry-extension.ts_
2. **`content-server` asks for the port optionally.** The askers are `EntriesService`, `EntryWriterService`, `EntryMatchQuery`, `PublicEntriesQuery`. With no extension present, content works as an ordinary non-localized CMS.
   _@Optional() @Inject(CONTENT_ENTRY_EXTENSION)_
3. **`i18n-server` binds the implementation.** The module is declared `global: true`, so the binding resolves inside content's (also global) module with no explicit import. The same inversion as `CONTENT_CATALOG` in Identity, with the roles swapped.
   _I18nModule.forRoot: { provide: CONTENT_ENTRY_EXTENSION, useExisting: EntryLocaleExtensionService }_
4. **The registration order is mandatory.** The plugin reads content's `CONTENT_REGISTRY` and binds its port.
   _apps/server/src/plugins.ts — I18nServerPlugin(config.plugins.i18n) comes after ContentPlugin_
5. **A missing extension is caught at startup.** If a type with `i18n: true` is registered but nobody bound the port, the application fails with an explicit message: “register a localization plugin after ContentPlugin, or drop the flag”. Otherwise the very first `create` would give a 500 on the NOT NULL `locale`.
   _EntryExtensionBootCheck (content-server)_

> **One binding, not a list**
>
> The port is designed for **one** provider per application. If a second extension is ever needed, the port's documentation prescribes binding a composite that fans the calls out: the port's shape (SQL fragments combined with AND, column sets merged) composes cleanly.

### Why synchronous rather than a domain event

This is an explicitly recorded decision, not an unfinished job. ADR-0003 moves plugins to a layered layout with aggregates, a unit of work and a transactional outbox — but just as explicitly notes that **layering is not obliged to turn a correct open-host port into an event**. Here the port is correct for four reasons:

#### The extension must be _inside_ the pipeline

Scoping a list adds a predicate to that very `WHERE`; stamping a creation appends columns to that very `INSERT`; the virtual filters take part in parsing `?filter=`. A subscriber learning of a write after the commit can physically do neither.

#### The rollback must be shared

Shared-field synchronization re-validates published siblings. A failure is a 422 and a rollback of the **whole** save. An asynchronous subscriber can no longer undo a committed edit — it could only leave a live translation invalid.

#### The lock must come first

`beforeWrite` is the **first statement** in the write transaction, before the pipeline's own row `UPDATE`. An event, by definition, arrives later — and by then a deadlock is already possible.

#### The caller needs the answer immediately

`afterUpdate` **returns the rewritten sibling rows**, and content's pipeline appends a revision for each — in the same transaction. Asynchronously there is nobody to receive that return value.

Separately: **revisions are written by content, not by i18n**, and that too is deliberate. Version numbering is serialized per entry by an advisory lock, and a second writer handing out numbers around it is exactly how duplicate versions appear.

### The contract: six hooks

Every method is called **unconditionally for every type**, so the implementation **must be a no-op for non-localized types** — otherwise binding the extension would change the behaviour of unrelated types. In `EntryLocaleExtensionService` every method opens with a `if (!type.i18n) return …` line.

| Hook            | When                                                                                             | What i18n does                                                                                                                                                                      | No-op                                                                              |
| --------------- | ------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| listScope       | synchronously, while assembling the list's `WHERE`                                               | validates `?locale=` (unknown → 400), takes the default when absent, scopes strictly; with `?localeFallback=default` widens through `OR … NOT EXISTS`                               | `undefined`                                                                        |
| createColumns   | `await`ed, before the `INSERT`                                                                   | stamps the validated `locale`; when a `localeGroupId` is passed it first checks the group really exists in this workspace (otherwise **404**), and only then joins the row to it    | `{}`                                                                               |
| beforeWrite     | the **first statement** of the create and update transactions                                    | takes a transactional advisory lock on `locale_group_id`                                                                                                                            | does nothing without a group either (a fresh creation has nothing to contend with) |
| afterUpdate     | inside the create **and** update transactions, after the columns and relation deltas are written | synchronizes shared fields/relations onto the siblings, demotes a rewritten published sibling to `draft`, re-validates the ones that **were** published; returns the rewritten rows | `[]`                                                                               |
| describeFanout  | outside a transaction, on the caller's request                                                   | a read-only answer to “what else will this write rewrite”: the names of the fields that travel, plus the siblings' locale slugs                                                     | `undefined`                                                                        |
| filterExtension | while parsing `?filter=`                                                                         | declares three virtual fields and resolves them into an `EXISTS`/correlated `count` over the group                                                                                  | `undefined`                                                                        |

### afterUpdate: what exactly travels

Three kinds of state, each computed **once** and applied to every sibling:

1. **Shared columns.** Identical in every locale. Copied verbatim.
   _sharedColumns() — scalars and media without the localized flag; a relation only if it is column-backed and Shared_
2. **Mirrored FKs of single relations.** The source's target is resolved to its own translation in the sibling's language. An unresolvable reference becomes `null` rather than continuing to point at the translation of the _previous_ entry — silently wrong data is worse than an empty field the editor can see and publication trips on.
   _mirroredColumnsByLocale() → RelationLinkService.equivalentIdsByLocale_
3. **Link sets of join-backed relations.** A mirrored link whose target has no translation in the sibling's language is simply **not set** — saving the English version must not fail because the German tag does not exist yet.
   _linkSetsByLocale() — Shared: verbatim; Mirrored: through the target's translation group, order preserved_

The mode is decided by the `relationLocaleSync(owner, spec)` rule, which lives in **content-server**: `None` if the owning type is not i18n, the relation is inverse, or it does not have `syncAcrossLocales` set; otherwise `Mirrored` if the target is i18n too, and `Shared` if not.

> **Four safeguards inside afterUpdate**
>
> **1.** Before reading anything (and, more importantly, before **locking** anything), it checks whether anything can travel at all — both entries are free. Otherwise every save of a localized type would take a `FOR UPDATE` on rows it was not going to write.
> **2.** A sibling for which all three kinds of state match is **not touched at all** — that guard is precisely what stops one save from re-issuing versions for the whole group. The comparison uses `IS DISTINCT FROM` (not `<>`), and every value is bound with **its own column's encoder** (`sql.param`): bare interpolation expanded an array-valued field (a jsonb multi-select, json, multiple media) into a _parameter list_, which Postgres read as a record and rejected.
> **3.** The “before the write” statuses are taken with a `SELECT … FOR UPDATE` **before** the synchronization: the `UPDATE` demotes the affected rows to `draft`, and a “was it published” check against the returned status would silently skip every one of them.
> **4.** A change to **relations only** still writes the row — that is how it earns its revision and its demotion.

#### Demoting a published sibling

**sibling published** → a shared field is edited → **draft, published_at preserved** = reads as **Modified**

Leaving the sibling `published` was not an option: the same edit would then be _live_ in the untouched languages and _pending_ in the edited one, and the sibling's freshly appended draft version would describe a row that declares itself published. `published_at` is preserved, so the sibling reads as **Modified** (live content + unpublished edits) rather than as a draft that was never published.

#### Creation pulls inward, not outward

On `context.created` the logic inverts: a new sibling arrives with the source's shared _values_ (the client copies them) but **with not a single relation** — relations never travel in a creation body. Propagating outward from such a row would push emptiness onto rows that were correct. So `inheritRelationsFromGroup` pulls relations **inward** from a donor — deterministically from the default locale's row if the group has one, otherwise from the lexicographically first. Columns are still propagated outward on creation — which is what makes a deliberately different shared value at creation time win.

The derived columns are meanwhile **appended to the `row` object in place**: the caller snapshots it for version 1 _after_ the call, and writing only to the database would leave the first version describing something the row never held.

### beforeWrite: why an advisory lock rather than an ORDER BY

This is the package's subtlest point. Synchronization locks every sibling with `FOR UPDATE`, and ordering _that_ statement does not save the group from deadlocks: by the time `afterUpdate` runs, the transaction **already holds a row lock** on the entry being edited — the pipeline's own `UPDATE` took it, before any i18n code. Two concurrent saves in two locales of one entry each hold the row the other is about to request, **whatever the order** in which siblings are selected: that first lock is not part of the ordered set.

> **The measured effect**
>
> Before the fix: **19 out of 60** interleaved cross-locale saves returned a 500 (`deadlock detected`, SQLSTATE 40P01). After: **0**. The lock taken in `beforeWrite` precedes every row lock, so the second writer simply **waits** — which is the correct outcome for two edits of one entry. Ordering siblings by id is still there in the code, but as a determinism guarantee rather than as the deadlock fix; the comment says so outright.

### describeFanout: the one hook nobody calls from the pipeline

A read-only twin of `afterUpdate` answering “what will this write rewrite besides the named row” **before** anything is written. The entries pipeline never calls it. It exists for the copilot's propose tools: under **ADR-0009** a proposal is applied at composition time, so one accepted edit of a shared field rewrites the entry in every language while the diff reads as an edit to one entry.

- **It filters the fields before any read** — a save touching only per-locale fields (that is, an actual translation) costs not a single query.
- **One self-join**, rather than “read the group id, then read the group”: the batch tool describes up to `BULK_MAX_SAVE_ITEMS` items per turn.
- **It takes no locks and does not filter on `deleted_at`** — no lock because the hook runs outside the write transaction and its answer is advisory by construction; deleted rows are not filtered out because `propagateToSiblings` rewrites trashed siblings too, and omitting them would understate the very change the hook exists to disclose.
- **It returns `undefined` rather than an empty description** when the row is alone in its group: a caveat on every edit would teach the reader to scroll past it on the one edit where it matters.
- **`travelsToSiblings` is deliberately broader than `sharedColumns`**: shared columns, mirrored FKs and link sets are applied by three different mechanisms, but to a human it is one fact — a value set here will end up over there.

### filterExtension: three virtual fields

| Field         | Type                            | Allowed operators               | SQL                                                               |
| ------------- | ------------------------------- | ------------------------------- | ----------------------------------------------------------------- |
| hasLocale     | an enum of the configured slugs | `eq` `in`                       | `EXISTS` a sibling in the named locale                            |
| missingLocale | an enum of the configured slugs | `eq` `in`                       | `NOT EXISTS`; `in` means **“all of the listed ones are missing”** |
| localeCount   | a number                        | `eq` `ne` `gt` `gte` `lt` `lte` | a correlated `count(*)` over the group                            |

> **Why ne / nin were taken away from hasLocale**
>
> They used to be allowed and read as a negation of “this locale exists” — but that is not a negation. They quantify **inside** the `EXISTS`: `hasLocale ne "de"` renders as `EXISTS(sibling WHERE locale <> 'de')` — “the group has some locale other than German”, which **a fully translated entry satisfies**. The question “show me entries without German” returned precisely the German ones. Absence is expressed by the `missingLocale` field, so the negations now give a 400 naming the field — a visible, correctable refusal instead of a quietly different answer. The admin's `useLocaleFilterFields` mirrors this restriction so that the drawer does not offer a rule the API will reject.

The group subquery is bounded by the **configured** set of locales — exactly as `configuredScope` is in the coverage query. Without that, two views of one entry diverged: a row in a slug the host had already dropped pushed `localeCount` above the configured total, and an entry the coverage card declared fully localized matched neither `localeCount eq 3` nor any `hasLocale` consistent with it.

## 07. How far locales reach

The plugin affects four surfaces, and in three of them its code takes no part at all — it merely explained to content, once, what a locale is.

### Localized entries and locale groups in content

- **The type flag `i18n: true`** is the only switch. It adds two columns, the unique index `(locale_group_id, locale)`, and a locale-scoped unique index for one-to-one.
- **The envelope keys are not editable.** The save DTOs (both the internal and the public one) list `locale` and `localeGroupId` among the reserved keys outright: they cannot be set through `values`. `locale` arrives as a separate body field/parameter, `localeGroupId` as a separate body field on creation.
- **A single and a collection behave the same** — a single simply resolves its one row by the active locale.
- **Revisions know about the group** — `locale_group_id` is in the revisions table, and a sibling rewritten by synchronization gets its own version.

### The public API

| Surface                       | How the locale is expressed                                                                                                                                                                                                                                                                                                      | Refusal                                                                        |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| REST public-api               | `?locale=` and `?localeFallback=` go **verbatim through the port**; `PublicEntriesQuery` simply adds the extension's `listScope` to its own visibility predicate                                                                                                                                                                 | an unknown slug → 400 (decided by `LocalePolicy`)                              |
| REST, `?translations=preview` | attaches the group's siblings as `translations`; **one** query per page through `locale_group_id IN (…)`; built on `liveWhere` rather than `readableWhere` — otherwise the scope would pin the read to one locale, which a translation lookup must not do. Nothing else about visibility changes: a draft locale stays invisible | on a non-localized type — a 400 reading “type is not a localized content type” |
| GraphQL                       | `locale` and `localeGroupId` are envelope fields that appear only on an i18n type; the `translations` field serves the group's **other published** rows, sorted by slug (the entry itself is not repeated)                                                                                                                       | a type without i18n simply does not have these fields in the schema            |
| GraphQL, relation deltas      | the `LOCALE_GROUP` enum: ids in a delta are read as translation-group ids and resolved to the group's row **in the source entry's language**                                                                                                                                                                                     | —                                                                              |
| MCP                           | `i18n_locales_list` is available to an external agent; `content_translations` is MCP's own tool, **published only**                                                                                                                                                                                                              | `i18n_translations_get` is closed to MCP (see section 10)                      |

### Content transfer

The transfer document carries a locale as two service fields on an entry: `$locale` (the row's slug) and `$localeGroup` (the original group id). Siblings within one document share a `$localeGroup`, and **that is how the importer reconstructs the group** without inventing a locale-matching rule.

- **The locale is part of the natural key.** On a localized type, key values are unique within a locale rather than within a group — otherwise `en/hello` and `de/hello` would collide. The key fingerprint explicitly separates two locales of one key, and a missing locale forms **its own bucket** rather than “any locale”.
- **Locale depth is a separate switch.** `TransferDepth` has two independent flags: `locales` (take the selected entries' siblings) and `relationLocales` (take the related entries' siblings too).
- **Locale siblings are depth 0.** A locale sibling of a selected entry counts as something “the user selected themselves” rather than as pulled-in context.
- **CSV knows these fields.** In the flat format `$locale` and `$localeGroup` are ordinary service columns.

> **There is no i18n code in transfer**
>
> `transfer-server` writes everything through content's `EntryWriterService`, and therefore passes through the bound extension — with locale stamping, the group check, the unique index and shared-field synchronization. An import cannot outrun validation, the workspace scope, or the caller's own permissions.

## 08. Scenarios step by step

### Scenario A. An editor creates the German translation of an article

1. **They open the English article.** The “Locale” panel in the right column shows three rows: English (the current one, ticked), Deutsch (dimmed, “Add”), Français (dimmed, “Add”).
   _GET /api/content/article/:id · GET /api/i18n/content/article/:id/locales_
2. **They click “Deutsch”.** If the form has unsaved edits, the **application-wide** navigation guard fires, not a local dialog.
   _beginLocaleSwitch → an overlay covers the page → navigate() after ~220 ms_
3. **A creation form opens, tied to the group.** The source's values travel in the router's state; `translateFromLocale` travels with them, because shared fields are about to be copied into a row of a _different_ language and the destination editor would otherwise have no way to know which language they are in (WCAG 3.1.2).
   _/content/article/new?locale=de&localeGroupId=<gid> · router state.translateFrom + translateFromLocale_
4. **The editor translates the localized fields and hits Save.** There is **no** separate “create a translation” call: this is an ordinary draft save.
   _POST /api/content/article with body.locale and body.localeGroupId (createBodyKeys)_
5. **Server: beforeWrite takes the group lock.** The first statement of the transaction.
   _pg_advisory_xact_lock(LG, hashtext(gid))_
6. **createColumns checks the group and stamps the locale.** A typo in the id cannot spawn a stray one-row group.
   _assertGroupExists → 404 if the group is not in this workspace; otherwise locale='de', localeGroupId=gid_
7. **INSERT. A duplicate locale is caught by the unique index.** The arbiter is the database, not a “count first, then write” check.
   _(locale_group_id, locale) → 23505 → 409_
8. **afterUpdate in created mode: relations are pulled inward.** The new translation gets the links the entry already had.
   _inheritRelationsFromGroup: the donor is the default locale's row; the derived columns are appended to row in place_
9. **Columns propagate outward; version 1 is snapshotted afterwards.** Matching siblings are not touched.
   _propagateToSiblings({relations: false})_
10. **A 201 response, a redirect to the new row's editor.** Deutsch is now a switcher row with a Draft badge.
    _The locale panel is re-read on entry.updatedAt_

### Scenario B. Editing a shared field in one locale

1. **The editor changes the price (a field without `localized`) on the German row and hits Save.**
   _PATCH/PUT /api/content/product/:id_
2. **beforeWrite takes the group lock — before the pipeline's row UPDATE.**
   _a concurrent save of the English row will wait here rather than deadlock_
3. **The pipeline writes the row and the relation deltas.**
   _UPDATE … RETURNING_
4. **afterUpdate decides whether there is anything to propagate — before any read.** On a type with no shared fields and no synchronized relations the query never runs at all.
   _shared.length || canSyncRelations; otherwise it exits with no FOR UPDATE_
5. **The siblings are selected with FOR UPDATE, ordered by id.** The **pre-write statuses** are taken here too.
   _including the soft-deleted ones — so a restore comes back consistent with the group_
6. **For each sibling: relations first, then columns.** A fully matching sibling is skipped — it gets neither a history entry nor a demotion.
   _IS DISTINCT FROM with sql.param under the column's encoder_
7. **A rewritten published sibling is demoted to draft, published_at is preserved.** The English row reads as **Modified**.
   _status: 'draft', updatedAt: now()_
8. **Siblings that _were_ published are re-validated.** A failure → a **422** with per-field issues and the text “Shared fields would invalidate the published "…" translation”, and **the whole save is rolled back**. Drafts need no validation — the same rule as when saving a draft directly.
   _EntryValidationService.validate(toRecord(...))_
9. **The rewritten rows are returned to the pipeline, which appends a revision for each.** A sibling's history does not skip the change, and a later restore will not silently undo it.
   _in the same transaction_

### Scenario C. The copilot translates an entry into three languages in one turn

1. **The model calls `i18n_locales_list`.** The slugs are deployment configuration; they are in neither the schema nor the system prompt.
   _requires: content:read · effect: read · surfaces: not specified → both the copilot and MCP_
2. **The model reads the source and calls `i18n_propose_bulk_translation`.** Five languages of one entry and eight entries in one language are the same list.
   _items[{id, locale, values}], ≤ BULK_MAX_SAVE_ITEMS · requires: content:update_
3. **The tool checks everything before anything is written.** A refusal fails the **whole** call and writes nothing — which is why retrying a corrected batch is safe.
   _the type grant → the type is localized → the slug is configured → the group is read once per unique id → the locale is not taken yet → two items do not target the same slot → localized fields only_
4. **The tool returns a `ProposalDraft` without writing anything.** The prefix is needed because the card keys its rows by `field`, and five languages translating `title` would collapse into one row.
   _kind: 'i18n.entry.bulk-translate' · changes prefixed with items[i].field_
5. **The run engine records the proposal and **applies it immediately** (ADR-0009).**
   _BulkTranslationProposalApplier_
6. **The applier re-reads the grant, then walks the items sequentially.**
   _each entry takes the workspace's shared content lock plus the group's advisory lock, so fanning out would only contend with itself_
7. **For each item: the source's shared values are read, and the translation is laid over them.** Read **at apply time** rather than frozen into the proposal: a shared field may have been edited between composition and application.
   _sharedValues(): localized fields, many/inverse relations, and any relation with a per-locale id are skipped_
8. **Creation goes through the same `EntryWriterService.create` as HTTP.** Which is why a duplicate `(group, locale)` is a clean 409 rather than a corrupted group.
   _no second write mechanism_
9. **The very first error stops the batch and throws.** A proposal has one row and one status, so there is no per-item verdict, and “nothing was saved” would be a lie about the rows already written.
   _“Translation 3 of 5 (fr) failed: … The first 2 were saved and the rest were not.”_

> **Why the applier must read the source — the costliest mistake in this package**
>
> The propose tool accepts **localized values only**. But a creation is a whole row: `coerceValues` stamps every declared field, and a shared field nobody sent arrives as `null`, not as “absent”. That breaks two things at once: the new row fails its own required check (`tag.slug` is required _and_ shared, and no tag translation carries it), and — worse — the extension takes that `null` for a shared value the save _carries_ and pushes it onto every sibling in the group. A published sibling is re-validated and fails the creation with a rollback, but **a group of nothing but drafts has no such protection — and the shared field is silently nulled in every language**. Which is exactly why the content tools **lost** their `localeGroupId` argument: the i18n tools are now the only entrance, and the content appliers refuse to join a saved group.

### Scenario D. Switching the language of the records table

1. **The user opens the switcher in the toolbar.** The rows have `tabIndex={-1}` so that a long list of locales does not become a Tab obstacle course.
   _a Popover + an ordinary Input + a role="listbox" list; focus stays in the search box, ↑/↓ move aria-activedescendant, Enter selects_
2. **They pick Deutsch.** Re-picking the active locale is a no-op, except when the URL holds an unknown slug: there it is the one click that clears the bad parameter, and it must not be skipped.
   _beginLocaleSwitch('Deutsch', apply) — apply is deferred by COVER_MS_
3. **The overlay covers the page, and only then does the URL change.** The default locale is written as a **clean URL** — the server scopes to the default when the parameter is absent anyway.
   _updateParams({ locale: toLocaleListParam('de', 'en') }) → ?locale=de_
4. **The server scopes the list strictly.** Untranslated groups are not shown.
   _listScope → WHERE locale = 'de'_
5. **The overlay holds until the requests settle.** The floor is needed because “no requests” right after the swap only means the requests have not been issued yet; the ceiling stops a hung request from leaving the page covered forever.
   _useIsFetching() → settleLocaleSwitch(), a floor of MIN_HOLD_MS = 380 ms, a ceiling of MAX_HOLD_MS = 5000 ms_

## 09. HTTP API

**Four routes, all reads.** The plugin has no write route at all: creating a translation is a `POST /api/content/:typeName` with a `localeGroupId` in the body.

| Method and path                                 | Guards                                                      | Permission   | Response                                                                                                                                                                     | Refusals                                                                                                                                                   |
| ----------------------------------------------- | ----------------------------------------------------------- | ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET /api/i18n/locales                           | `session`                                                   | —            | `{ items: [{ slug, name, isDefault, dir }] }` in config order                                                                                                                | —                                                                                                                                                          |
| GET /api/i18n/content/:typeName/:id/locales     | `session` `PermissionsGuard` `WorkspaceGuard`               | content:read | `{ localeGroupId, items: [{ locale, dir, isDefault, entry }] }` — one item per **configured** locale; `entry` is either `{ id, status?, publishedAt?, updatedAt }` or `null` | 404 — unknown type; **400** — the type is not localized; 404 — the entry does not exist or is trashed/in another workspace; 400 — a non-UUID in `:id`      |
| POST /api/i18n/content/:typeName/locale-summary | `session` `OriginGuard` `PermissionsGuard` `WorkspaceGuard` | content:read | **200** (not 201): `{ groups: { <groupId>: [{ locale, entryId, status?, publishedAt? }] } }`                                                                                 | 400 — the type is not localized; 400 — a non-UUID in `groupIds` or more than `LOCALE_SUMMARY_MAX_GROUPS = 100` of them; 403 — no `Origin`/a foreign Origin |
| GET /api/insights/i18n/coverage                 | `session` `PermissionsGuard` `WorkspaceGuard`               | content:read | `{ locales[], records, localized, notLocalized, requiresLocalization, types[] }`                                                                                             | —; there is **no** `?days=` parameter                                                                                                                      |

> **Why the summary is a POST that answers 200**
>
> A page's worth of uuids does not fit in a query string, so the list of groups travels in the body. But this is a read — hence 200, not a 201 that would claim something was created. The response's keys are **exactly** the request's: every requested id is pre-seeded with an empty array, and the rows are workspace-scoped — so a group from another workspace and an id that means nothing come back identically. The caller learns nothing it did not send.

### Why coverage hangs under `insights/` rather than under `i18n/`

The Insights page's endpoints are grouped **by what they are**, next to the content and media ones — a reader looking for a card's data finds it beside the other cards' data. The flip side: the route name does not hint which plugin owns it. i18n does, and for a substantive reason — coverage is a question about the **configured** set of locales, and content-server knows nothing about what a locale means: it can report which slugs _occur_ in the data, but not which are _missing_. And absence is the entire widget.

### The four rules the coverage query encodes

- **C-01** — **The unit of counting is an entry, not a row.** A localized entry is one row per language, so counting rows would report 40 pieces in 3 languages as 120 objects and void the meaning of every ratio. Everywhere it is `locale_group_id` that is counted, through `count(distinct)` — the distinct keeps the figure honest on a paranoid type, where the index is partial and a trashed row would otherwise be counted twice.
- **C-02** — **Rows in an unconfigured locale are filtered out.** That is what makes “fully localized” mean what it says: a dropped slug covers nothing, and keeping it would push the group's distinct-locale count above the configured total — so an entry could be “over-covered” and still not count as complete. A group made entirely of such rows drops out — which is the right answer, rather than an entry with zero languages.
- **C-03** — **`notLocalized` is a subset of `requiresLocalization`, not a second slice.** An entry that exists in one of four languages both has no translation at all and needs translations. They are different figures because they are different work. With **one** configured locale `notLocalized` is forced to `0`: there is nowhere to translate to, and otherwise every entry would report itself as both fully localized and not localized at all.
- **C-04** — **The per-type rows partition the workspace total.** Each type's `requiresLocalization` sums to the envelope's; the same for the rest. That is what makes the card's two breakdowns one story rather than two. The server-e2e test checks the sum — a per-type figure that diverges from the total is exactly the kind of wrongness a dashboard gets believed about.

The implementation: the group's expansion (`records` / complete / single) is one grouped subquery, folded by an outer aggregate. Reading a row per group and counting in JS would drag the workspace's entire content over the wire for three integers. A type the workspace never used is **omitted** rather than shown as a zero — the same rule the content pipeline applies.

## 10. Agent tools

Four tools in the shared `@apograph/tools-server` registry, registered from `I18nModule.forRoot`. The registry is injected `@Optional()` — a deployment with neither the copilot nor MCP is fine, and the tools simply do not register.

| Tool                          | effect    | surfaces                                    | requires       | What it does                                                                                         |
| ----------------------------- | --------- | ------------------------------------------- | -------------- | ---------------------------------------------------------------------------------------------------- |
| i18n_locales_list             | `read`    | **field absent → both the copilot and MCP** | content:read   | serves the configured locales with their slugs and default flag                                      |
| i18n_translations_get         | `read`    | \['copilot'\]                               | content:read   | one item per configured locale: whether a translation exists, its id and its publication status      |
| i18n_propose_translation      | `propose` | \['copilot'\]                               | content:update | an `i18n.entry.translate` draft: one entry into one locale                                           |
| i18n_propose_bulk_translation | `propose` | \['copilot'\]                               | content:update | an `i18n.entry.bulk-translate` draft: up to `BULK_MAX_SAVE_ITEMS` entry × locale pairs as one change |

> **Two read tools sit in one file and land on different surfaces**
>
> **`i18n_locales_list` is given to MCP too.** It returns deployment configuration, the same for everyone, with no workspace data and no publication state — there is nothing to leak. And an external agent needs it for exactly the reason the copilot does: `?locale=` on public reads takes a slug that appears in no schema and no prompt, so without the list a client either omits the parameter and silently reads the default language, or guesses and gets an error.
>
> **`i18n_translations_get` is copilot-only.** `LocaleGroupService.entryLocales` builds its predicate from `liveWhere`, which scopes workspace and soft-delete but **not publication state** — that is, it reports a draft sibling _and its status_. An MCP token with `read` must not see that (MCP's own `content_translations` is published-only), and narrowing the tool to published content would take the answer away from the copilot, which is where it is useful.
>
> The deciding question is always the same: **what would this tool show a token holding `content:read`** — not “which consumer asked for it”.

### What the propose tools check themselves

Under ADR-0009 a change is applied at composition time, so the tool's checks are the **last ones before the write**:

- **The type's grant and its existence give one message.** “Unknown type in this workspace” answers both “no such type” and “it is not granted here” identically, so that a run cannot enumerate the deployment's types.
- **“Not localized” is a separate explicit error.** It describes a type the caller has already proved it can reach, and it is safe and useful to say. An empty `[]` would read as “this one has no other languages”, when the truth is “this content is not translated at all”.
- **The slug is resolved against the configured set**, with a “call `i18n_locales_list`” hint.
- **The locale must not already exist in the group** — otherwise a direct instruction: “use `content_propose_update` on that row”.
- **Shared fields are refused.** A shared field is by definition one per group, so “translating” it would either be ignored or silently rewrite every sibling. The message lists both the rejected fields and which fields on this type actually do vary by locale.
- **An empty value set is an error too.**

#### Three checks specific to the batch

- **The group is read once per unique source `id`.** Five languages of one entry ask an identical question; nothing is written during propose, so the **whole view** is cached, not just the group id.
- **Two items targeting the same `(group, locale)` slot are rejected up front** — otherwise they would collide with the unique index halfway through applying, once the first translations had already been written.
- **Every error is prefixed with the item's number** (`Item 3: …`), and a refusal fails the whole call.

#### ENTRY_PARAMS_SLOT — three different things in one contribution

The locale comes from the saved entry (edit mode) or from the creation form's `?locale=` (a draft translation has no `entry` yet) — so the picker stays “in language” in both modes.

### The locale switcher in the entry editor

| Locale row                            | Appearance                                                            | Action                                                     |
| ------------------------------------- | --------------------------------------------------------------------- | ---------------------------------------------------------- |

| no translation, `content:create` held | a dimmed name + “+ Add”                                               | re-targets the form: `/:type/new?locale=…&localeGroupId=…` |
| no translation, no permission         | an inert row reading “Not translated — you can't create translations” | none                                                       |
| the group's membership did not load   | an inert row reading “Unknown — couldn't load”                        | none; not-knowing **outranks** permission                  |

Every navigation appends the `tabSegment` from the slot's context — a switch made from the Relations tab lands on the sibling's Relations tab rather than dumping you on General. The section's footer shows the `localeGroupId` with an explanatory tooltip; on a fresh creation with no group yet, a dimmed note “Assigned when this record is saved.” stands in for the id.

> **An inert row must say why it is inert**
>
> It used to be an active row with `opacity-50`: a token chosen to barely clear 4.5:1 and then halved — **measured at 2.18:1** against the rail, below AA. It carried no text, so a _forbidden_ locale and a _missing_ one were the same dim line with no programmatic difference. Now the reason is real text at full contrast. `aria-disabled` would not do here: there is no control, and a `listitem` does not support it anyway.

### States: an error is not an emptiness

Three reads gate everything in the package, and each used to fail into something that read as an _answer_:

#### The locale list did not load

Every surface returned early, and the switcher — the only control that can clear `?locale=` — disappeared while the list stayed scoped to that locale. Now the switcher draws a retry button, and the title chip falls back to the row's own `locale` (it is a BCP-47 tag; it can name itself).

#### The group's membership did not load

Every locale resolved to “no sibling”, and the panel offered to _create_ a translation that already existed, whose save then answered 409. Now the panel says the membership did not load, and while that holds, no row is active.

#### The batch summary did not load

The “Locales” cell drew empty — which is exactly what “this entry has no other locales” looks like. Now it prints _Unavailable_ with a tooltip. The cell has three outcomes and three different renders, each with text a screen reader will read.

> **An unknown slug must not resolve to the default**
>
> The server answers 400 for an unconfigured `?locale=`. A switcher labelled “English” would describe a list it is not showing — and re-picking English was swallowed as “already active”, leaving no way out but editing the URL. Now the switcher reports the unknown slug (a warning icon, red text, a separate `aria-label` with instructions), and **any** selection is applied: `findLocale` returns `undefined` instead of falling back to the default, and `resolveActiveLocale` treats an empty `?locale=` as absent.

### Publication state: four, not two

Both surfaces that show a locale's status (`LocaleRow` in the panel and `LocaleBadge` in the column) render **content-admin's classifier** — `entryStatusView` / `ENTRY_STATUS_VIEW_VARIANT` / `EntryStatusBadge` — rather than their own `published ? … : …`. The server stores two values, but there are **four** states: a locale with live content plus unpublished edits reads as **Modified**, which a two-way branch silently collapsed into “Draft”. And here that is the common case: editing a **shared** field rewrites every sibling and moves the whole group into that state.

So both wire views carry `publishedAt` alongside `status` — that is the bit separating the two draft states. In the column's badge the state travels in the link's **accessible name** (the badge itself shows the slug, and colour alone says nothing), and as a **localized label** at that: `entryStatusView` returns a machine token, and interpolating it would insert a lowercase English word into an accessible name in any interface language.

### The data layer: four hooks

| Hook                    | Request                     | Cache                                                       | The subtlety                                                                                                                                                                   |
| ----------------------- | --------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| useLocales              | GET /i18n/locales           | `STALE_TIME.Forever`, a key without the workspace           | exposes **`isError` as part of the contract** rather than as a detail: without it a failed read would silently delete the whole feature                                        |
| useEntryLocales         | GET …/:id/locales           | key `[..., workspaceId, typeName, entryId]`                 | used by the panel and by both “all locales” menu items                                                                                                                         |
| useLocaleSummaries      | POST …/locale-summary       | the key includes the **sorted** unique ids                  | feeds both the column and the panel in creation mode; gated on the column's `isVisible` — otherwise the batch flew on every page for a column nobody had turned on             |
| useLocalizationCoverage | GET /insights/i18n/coverage | `STALE_TIME.Standard`, a key with the workspace, `retry: 1` | the workspace only reaches the server as an ambient header and is not sent on a cache hit — without the id in the key, switching workspaces would show someone else's coverage |

**There is no “create a translation” hook.** A sibling is created by the editor's ordinary Save/Publish; a 409 on a duplicate locale and a 404 on an unknown group surface through the normal save-error path.

### The “Translation coverage” card

Three headline figures on the left, a list of bars on the right, a **By language / By type** toggle. This is **a view switch over one payload**, not two cards and not a second request: “which language is behind” and “which content type the work is in” are asked by the same person a second apart, and splitting them across cards would arbitrarily assign the shared figures to one of them.

- **The axes have different denominators, and the legend changes for it.** By language, each bar scales to the workspace's record count — a bar's length is that language's reach. By type, it scales to the largest type, so length reads as “how much content is in this type” and the blue share as “how much of it is finished”. That is what makes “the debt sits in Article” visible.
- **The card's subtitle travels with the axis** — left on the language wording, it would describe a chart no longer on screen.
- **The three figures are not a partition, and the labels say so:** “in every language” / “no translations started” / “missing at least one”. Three questions, not three slices — which is also why it is not a pie chart.
- **An empty workspace does not get a green chip.** `requires === 0` is true both when everything is translated and when there are no records at all; the latter is not an achievement, and a workspace nobody ever wrote to was awarding itself “Fully translated”.
- **0% and 100% are reserved for the real values.** Ordinary rounding printed “0%” next to a visible bar (3 of 609) and “100%” next to a card whose chip said work remained (608 of 609). A near miss is clamped to 1% / 99%. Division happens only here at all — the server sends counts and never divides.

### The switch flourish

`LocaleSwitchOverlay` plus the module-level store `utils/localeTransition`. The trigger calls `beginLocaleSwitch(name, apply)`, passing **the swap itself** (`updateParams` in the toolbar, `navigate` in the widget) as `apply`, instead of performing it immediately.

- **The store is module-level, not React state** — a switch from the widget _navigates away_, unmounting the trigger, and the flourish has to survive that and be re-read by a fresh overlay host at the destination.
- **The host is page-level, not editor-level.** It nests in `CONTENT_OVERLAY_SLOT`, which `ContentLibraryPage` renders outside its routes. It used to be drawn inside the editor — which unmounts for its own loading, so the cover vanished mid-transition, exposing a full-page spinner, and came back after the re-render: two loaders blinking in turn.
- **The hold is data-driven, not timer-driven.** The overlay watches `useIsFetching()` and calls `settleLocaleSwitch()` when nothing is in flight; the `MIN_HOLD_MS` floor is needed because “no requests” before the destination's requests are issued means nothing, and the `MAX_HOLD_MS` ceiling stops a hung request from leaving the page covered.
- **A rapid re-switch cancels the deferred `apply`** — the last selection wins. Unmounting the trigger also cancels a swap that has not run yet, but **not** one that has: from that point the flourish is legitimately in flight.
- **Purely visual:** `pointer-events-none`, `motion-reduce:animate-none`, a portal into `document.body`, a `bg-background/95 backdrop-blur-sm` background.

### Language and direction in the markup

`localeAttrs(locales, slug)` yields the `{ lang, dir }` pair to spread onto any element rendering that locale's text: the switcher's rows and trigger, the name in the title chip, the panel's rows. **A locale's display name is written in that locale**, so it needs the markup before any content is open at all. The surrounding chrome copy (“(default)”, “Translated fields”) stays in the admin UI's language and is deliberately kept outside the marked-up element.

In the title chip the `·` separator sits **outside** the marked-up span, in the chip's own direction: inside it an RTL name dragged the separator to the wrong side of itself — the separator belongs to the chip's layout, not to the name.

The editor's row of translated fields carries `lang={entry.locale}` (through content's `EntryFieldSections`), with `dir="auto"` on both rows. **Field labels still inherit that `lang`** — marking up each control individually requires threading it through every branch of `EntryFieldInput` and is tracked as a separate task.

## 12. Configuration

i18n has **no environment variables at all**. The whole configuration is a literal object in `apps/server/apograph.config.ts` under the `plugins.i18n` key. That is deliberate: the set of locales is a stable product setting, not a secret and not per-environment tuning.

| Key                   | Type               | Default                | What it does                                                               |
| --------------------- | ------------------ | ---------------------- | -------------------------------------------------------------------------- |
| locales               | LocaleDef\[\]      | required               | the available locales in display order; exactly one with `isDefault: true` |
| locales\[\].slug      | string             | required               | a BCP-47 tag in lowercase form; stored in the `locale` column              |
| locales\[\].name      | string             | required               | the display name; written **in that language**                             |
| locales\[\].isDefault | boolean?           | false                  | exactly one locale must have `true`                                        |
| locales\[\].dir       | 'ltr' \| 'rtl' ?   | inferred from the slug | a declaration always beats the inference; always present on the wire       |
| orphanedLocales       | 'fail' \| 'warn' ? | 'fail'                 | what to do at startup if the data contains rows in an undeclared locale    |

### Removing a locale is the one change that fails silently

Adding a locale is safe and announces itself: groups get an empty slot, coverage shows `translated: 0`, the panel shows `entry: null`. Removing one is neither.

> **What happens when a locale is removed from the config**
>
> Nothing deletes the rows and nothing migrates them. From that second on **every reading path hides them**: `?locale=de` becomes a 400, the locale panel iterates the configured set, coverage and the virtual filters are bounded by it, the batch summary discards them. The German content is intact and reachable only through `psql`, and the product never mentions it again — including to the person who made the change: they see a shrunken locale switcher and nothing else.

`OrphanedLocaleChecker` computes that diff **once at startup** (`OnApplicationBootstrap`): per localized type, the distinct unconfigured slugs with their row counts, one `GROUP BY locale` per type, on a column the `(locale_group_id, locale)` index already covers. Trashed rows are counted too: a restore would bring back a row in a locale nothing can display — the same problem, merely deferred.

- **`'fail'` (the default)** — startup aborts with a message listing the configured slugs, each orphaned slug with its row count, and a hint to “set `'warn'` to boot anyway”. The choice (migrate the rows or bring the locale back) is put to whoever changed the config, while it is still their change.
- **`'warn'`** — the same report goes to the log and the application continues starting. For a deployment deliberately mid-migration.
- `findOrphans()` is public — a migration script or an operator endpoint can ask the same question without reinventing the rule.

## 13. Invariants

- **I-01** — **Exactly one default locale.** Checked at plugin construction (`LocaleSet.create`: `defaults.length !== 1` → `InvalidLocaleSetError`). Consequence: `LocaleSet.default()` is a total function, and no other code handles “what if there is no default”.
- **I-02** — **The locale set is non-empty and the slugs are unique.** An empty array and a duplicate slug fail in the same place, before startup, before the first request.
- **I-03** — **A locale slug is a BCP-47 tag in lowercase form.** `/^[a-z]{2,3}(-[a-z0-9]+)*$/`, no longer than 35. Nothing in the code upper-cases the region — the value is dropped into `lang` verbatim.
- **I-04** — **The writing direction is always present on the wire.** `dir` is optional in the config, but `Locale.dir` is always resolved (declared or inferred). A consumer sets `dir` unconditionally rather than guessing.
- **I-05** — **An unknown slug is a 400, never a substitution of the default.** The single gate is `LocalePolicy.resolve`, wrapped by `LocaleRegistryService.resolve`. The rule is mirrored on the client: `findLocale` returns `undefined` on a miss.
- **I-06** — **The absence of `?locale=` means the default locale.** Which is why the default locale is written as a clean URL in the admin UI (`toLocaleListParam`) — the two spellings cannot diverge.
- **I-07** — **The fallback chain is no longer than two.** Only `[requested]` or `[requested, default]`, and only with `?localeFallback=default`. There is no hierarchical fallback (`pt-br → pt → en`).
- **I-08** — **Every port hook is a no-op on a non-localized type.** All six methods open with a `type.i18n` check. Binding the extension cannot change an unrelated type's behaviour — that is a requirement of the port's contract, not a courtesy.
- **I-09** — **One row per `(group, locale)` pair.** The arbiter is the database's unique index (partial on paranoid types, `WHERE deleted_at IS NULL`), not a check in code. A duplicate is always a 409, never a corrupted group.
- **I-10** — **A `localeGroupId` on creation must name an existing group in this workspace** — otherwise a 404. A typo cannot spawn a stray one-row group. The TOCTOU window is harmless: the row stays valid, and duplicates are caught by the index anyway.
- **I-11** — **An ordinary creation starts its own group.** The id comes from the column's default (`gen_random_uuid()`) rather than from code — so “start a new group” and “join an existing one” differ by the presence of one argument.
- **I-12** — **The group lock is taken before any row lock.** `beforeWrite` is the transaction's first statement. Ordering siblings by id remains, but as determinism rather than as deadlock protection.
- **I-13** — **A save with nothing to propagate takes no sibling locks.** The “are there shared columns or a synchronized relation” check runs **before** the read. Both inputs are free: the columns come from the save's own value bag, and a relation's synchronizability is a property of the schema.
- **I-14** — **A sibling where everything matches is not rewritten.** No history row, no demotion, no `updatedAt`. The comparison uses `IS DISTINCT FROM`, with every value bound by its own column's encoder.
- **I-15** — **A rewritten published sibling goes to `draft`, keeping `published_at`.** It reads as **Modified**, not as a draft that was never published. Publishing any locale remains per-row; this rule merely stops one locale from going live on someone else's save.
- **I-16** — **A sibling that _was_ published must remain valid.** Re-validation reads the **pre-write** statuses taken with `SELECT … FOR UPDATE`; a failure is a 422 and a rollback of the whole save. Drafts need no validation — the same rule as when saving a draft directly.
- **I-17** — **An unresolvable mirrored relation is nulled, not left.** A left value would point at the translation of the _previous_ entry — silently wrong data is worse than an empty field.
- **I-18** — **A mirrored link to an untranslated target is simply not set and does not fail the save.** An English save must not fail because the German tag does not exist yet. That is `equivalentIdsByLocale`'s job — the lenient twin of `resolveLocaleGroups`, which throws a 422 (right for an explicit API call, wrong for implicit synchronization).
- **I-19** — **Creation pulls relations inward rather than pushing them outward.** The donor is picked deterministically: the default locale's row, otherwise the lexicographically first. The derived columns are appended to `row` in place, because the snapshot for version 1 is taken after the call.
- **I-20** — **Revisions are written by content, not by i18n.** `afterUpdate` returns the rewritten rows and the pipeline appends a version for each in the same transaction. Numbering is serialized by an advisory lock; a second writer handing out numbers around it is a way to produce duplicate versions.
- **I-21** — **`hasLocale` accepts only `eq` and `in`.** `ne`/`nin` negate _inside_ the `EXISTS` and answer a different question. The refusal is a 400 naming the field. The admin drawer mirrors the same restriction so as not to offer a rule the API will reject.
- **I-22** — **`missingLocale in [a, b]` means “all of the listed ones are missing”.** It is a `notExists` over the union. “At least one is missing” is expressed as an `or` of `missingLocale eq` rules.
- **I-23** — **The virtual filters and coverage are bounded by the same configured set.** The extension's `groupScope` and the coverage query's `configuredScope`. Without this the two views of one entry would diverge: `localeCount` would drift above the configured total.
- **I-24** — **Coverage's unit is an entry, not a row.** `count(distinct locale_group_id)` everywhere. The per-type rows sum to the envelope's totals — a dedicated server-e2e test checks this.
- **I-25** — **With one configured locale, `notLocalized` is forced to 0.** Otherwise every entry would report itself as both fully localized and not localized at all.
- **I-26** — **The summary response's keys are exactly the request's keys.** Every requested id is seeded with `[]` and the rows are workspace-scoped: another workspace's group and a non-existent id are indistinguishable.
- **I-27** — **The agent's tools re-check the type grants, the HTTP path does not.** A type name from the model is steerable by the content it read; a type name from the UI has already passed a workspace-scoped controller.
- **I-28** — **A propose tool accepts `localized` fields only**, and the applier must mix in the source's shared values, read **at apply time**. Otherwise `coerceValues` stamps the shared fields as `null`, and a group of drafts is silently nulled in every language.
- **I-29** — **The batch applier writes sequentially and stops at the first error**, naming how many landed. A proposal has one row and one status — there is no per-item verdict.
- **I-30** — **An error is not an emptiness.** The admin's three reads (`useLocales`, `useEntryLocales`, `useLocaleSummaries`) must distinguish “no data” from “couldn't ask”, and every surface draws that as its own state.
- **I-31** — **Cross-locale relations are forbidden.** The picker's candidates are scoped strictly by the active locale, with no fallback. Correspondingly, the applier does not copy the source's per-locale relations.
- **I-32** — **The plugin owns no table and ships no migration.** The absence of a `drizzle.config.ts` is part of the package's contract, not an oversight.

## 14. Testing checklist

Laid out by level: unit (no database), server-e2e (needs Docker — a Postgres testcontainer), admin-e2e (a mocked API, no backend), and manual checks on a live stand.

### Unit — `npx nx test @apograph/i18n-server`

- **Config validation at construction** — an empty locale array, a duplicate slug, zero defaults, two defaults, a malformed slug (`EN`, `pt_BR`, `e`), an empty name, a `dir` outside `ltr|rtl`: all fail on the `I18nServerPlugin()` call, not at startup
- **Direction inference** — `ar`/`he`/`fa`/`ur` → rtl; `az-arab` → rtl; `ku-latn` → ltr; an explicit `dir` beats the inference
- **`LocalePolicy.resolve`** — no slug → the default; a known one → itself; an unknown one → `UnknownLocaleError`
- **`shouldWidenToDefault` / `fallbackChain`** — fallback requested and the locale is not the default → a chain of two; requested == default → one; fallback not requested → one
- **`LocaleSet.remove`** — refuses to delete the default, refuses to delete a non-member
- **The propose tools** — `translation-proposal.provider.spec.ts`: refusal on a shared field, refusal on empty values, refusal on a taken locale, refusal on two items in one slot, the `Item N:` prefix, exceeding `BULK_MAX_SAVE_ITEMS`

### Server-e2e — `apps/server-e2e/src/server/i18n/`

- **The locale list** — serves the configured ones, exactly one `isDefault`
- **Stamping on creation** — with no `locale` the default is taken; an explicit locale is stamped; an unknown one → 400; an ordinary creation gets its own fresh group
- **List scoping** — with no `?locale=` the default only; with `?locale=de` strictly German; an unknown slug → 400; `?localeFallback=default` substitutes the default row where the requested one is missing — and exactly one per group
- **Creating a sibling** — a new draft with a shared group; a duplicate locale → **409**; an unknown target locale → 400; a `localeGroupId` that names no group in the workspace → **404**
- **Shared-field synchronization** — a shared field travels to the siblings, a `localized` one does not; an array-valued (jsonb) shared field synchronizes without breaking the predicate; re-sending an unchanged array does not touch the siblings
- **Revisions** — a version for every rewritten sibling; when only a `localized` field is edited, the siblings' histories are not touched at all
- **Demotion and validation** — a rewritten published sibling goes to draft with `publishedAt` preserved; a draft sibling and its `publishedAt` are untouched; a synchronization that would make a published sibling invalid → **422** and a full rollback
- **Relation synchronization** — a shared many-relation travels to all; unlinking travels too; a new translation inherits the group's relations; a new translation does **not** erase the relations it did not arrive with; a mirrored many and a mirrored single are laid out per locale; a mirrored link to an untranslated target is dropped and the save succeeds; an unsynced relation stays independent per locale
- **One-to-one per locale** — one entry shares a target across its own locales; a target already taken **in the same locale** is rejected; soft-deleting the holder frees the target
- **The schema exposes the sync mode** — so the editor can explain its own behaviour; on a type without locales nothing is said about locales
- **The virtual filters** — `hasLocale`/`missingLocale` select by group membership; `localeCount` compares the number of translations; `hasLocale ne` → 400
- **The panel and the summary** — one item per configured locale (present or null); a batch per page of rows; both routes → 400 on a non-localized type
- **Non-localized type regression** — `?locale=` is ignored on an ordinary type
- **Locale integrity** — `i18n-locale-integrity.spec.ts`: concurrent cross-locale saves produce no `deadlock detected`
- **RTL** — `i18n-rtl-locales.spec.ts`: `dir` arrives in the list and on the panel's items
- **A single locale** — `i18n-single-locale-coverage.spec.ts`: `notLocalized` equals 0
- **Coverage** — `apps/server-e2e/src/server/insights/localization-insights.spec.ts`: the entry-versus-row fold and the per-type sum matching the envelope's total
- **Orphaned locales** — rows in an undeclared slug: `'fail'` aborts startup with the listing, `'warn'` logs the same report and continues; trashed rows are counted too

### Admin-e2e — `apps/admin-e2e/src/content/i18n.spec.ts`

- **The switcher** — not drawn on a non-localized type; not drawn with a single configured locale; on a read error it draws a retry button; an unknown `?locale=` is shown as such and any selection is applied
- **The switcher's keyboard** — focus stays in the search box, ↑/↓ move the highlight, Enter selects, the rows do not catch Tab
- **A clean URL for the default** — picking the default locale removes `?locale=` rather than writing `?locale=en`
- **The locale panel** — the current one is ticked; an existing one leads to the sibling; a missing one leads to a creation form with `?locale=` and `localeGroupId`; the `tabSegment` is preserved
- **Inert rows** — without `content:create` the row says translations cannot be created; when the membership read fails — “Unknown”, and that outranks permission
- **A status badge only on a publishable type** — on an always-live type the row draws no badge at all
- **Modified rather than Draft** — a locale with `status: draft` and a non-empty `publishedAt` must read as Modified both in the panel and in the column's badge
- **The Locales column** — off by default; when on it makes **one** POST per page; when off it makes none; the three states (loading / Unavailable / badges) are distinguishable
- **The “all locales” menu** — “Publish all” is hidden with a single locale, “Unpublish all” is hidden when nothing is live; the dialog's rows are labelled by locale rather than by identical headings
- **The coverage card** — `apps/admin-e2e/src/insights/insights.spec.ts`: toggling By language / By type changes the bars, the legend and the subtitle together; an empty workspace gets no green chip
- **Accessibility** — axe with no violations on the editor with the panel and on the table with the column; a locale's name carries `lang`/`dir`; the publication state is in the badge link's accessible name and is localized

### Manual checks on a live stand

- **The flourish** — switching to a locale with a cold cache: the editor's spinner must not flash out from under the cover; a rapid re-switch — the last selection wins; clicking an unrelated menu item while the cover is up must not drag you to the abandoned locale
- **Deadlocks** — two tabs, two locales of one entry, simultaneous saves of a shared field: the second waits, both succeed, no 500 appears
- **The 422 rollback** — an edit to a shared field that breaks a required rule in a published sibling: not one row must change
- **RTL** — add `{ slug: 'ar', name: 'العربية' }` with no `dir`: the direction must arrive as `rtl`, and the title chip must not drag the separator
- **Removing a locale** — drop `fr` from the config with French rows present: startup must fail with a listing of the types and row counts
- **The copilot** — “translate this into German, French and Spanish”: **one** change card, one run step; the answer for a non-existent language must point at `i18n_locales_list`; translating a shared field must be refused with a listing of the genuinely localized fields
- **Transfer** — an export with locale depth on and an import into a clean workspace: the groups must be reconstructed, and two locales' natural keys must not collapse

## 15. Boundaries of responsibility

| Question                                                                            | Answered by                                    | Not answered by                                                        |
| ----------------------------------------------------------------------------------- | ---------------------------------------------- | ---------------------------------------------------------------------- |
| Which locales exist, which is the default, how an unknown slug reads                | i18n-server (domain/)                          | —                                                                      |
| Whether a type has `locale`/`locale_group_id` columns and which indexes are on them | content-server (table-builder)                 | i18n                                                                   |
| Whether a relation counts as synchronizable and how (`Shared`/`Mirrored`/`None`)    | content-server (relationLocaleSync)            | i18n — only the machinery that applies it                              |
| Who writes a sibling's revision                                                     | content-server                                 | i18n — it only returns the rewritten rows                              |
| Who permits a write and under which permission                                      | identity-server + content-server               | i18n — it introduces no permissions of its own                         |
| Whose workspace this is                                                             | workspaces-server (WorkspaceGuard)             | i18n                                                                   |
| What a publication status badge looks like                                          | content-admin (entryStatusView)                | i18n-admin — it reuses the classifier                                  |
| Who draws the Insights page                                                         | insights-admin                                 | i18n-admin — only one card                                             |
| Who carries locales in export/import                                                | transfer-\*                                    | i18n — but every imported entry goes through the bound port            |
| Who proposes and applies an agent's translation                                     | i18n-server (copilot/)                         | —; the content tools were **stripped** of the `localeGroupId` argument |
| Who translates the text                                                             | a human or a model                             | i18n — it calls no translator                                          |
| The admin UI's own language                                                         | bootstrap-admin (react-intl, one IntlProvider) | i18n — it localizes content, not the UI                                |

### What the package does not have and, by the current code, does not plan to

- **No hierarchical fallback.** `pt-br` does not fall back to `pt`. The chain is at most two: the requested one and the default.
- **No locale-management UI.** Locales are a literal in the host's code, not a database row. The server's comment names a future per-locale settings table outright as “the first candidate” if owning tables is ever needed.
- **No locale-deletion operation.** Only a diff and a boot-time check.
- **No translation-creation route of its own.** Joining a group is what the `localeGroupId` argument already means.
- **No per-locale permissions.** You cannot give an editor access to German only.
- **No “needs translation” status on an entry.** The backlog is computed by query (coverage, the virtual filters) rather than stored as a flag.
- **No domain events and no outbox** — there is nothing to write, and that is recorded explicitly as a decision rather than as deferred work.

## 16. Divergences between code and documentation

Every statement from `AGENTS.md` and the JSDoc was checked against the implementation. Below is where they diverged. None of the divergences is a behavioural defect; all of them mislead the reader.

| File                                                       | What it says                                                                                                                                    | What the code does                                                                                                                                                                                                                                                                        |
| ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

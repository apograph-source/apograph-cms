# 0006 — The CMS is an MCP server, over one shared tool registry

- **Status:** Accepted
- **Date:** 2026-08-08
- **Deciders:** Engineering

## Context

The CMS already has a complete external content API: `/api/v1/*`, authenticated
by the bearer tokens the admin's API Tokens page mints, with content CRUD,
schema discovery, workspace buckets, and grant-scoped visibility. Anything a
script can do to this CMS from outside, it can do there.

Agents cannot use it. An MCP client discovers what a server can do by asking it;
it does not read an OpenAPI document and synthesise a REST client. So the
practical question is not "should agents be able to edit content" — they already
can, with a token and an HTTP library — but "do they get a described, permission-
filtered surface, or does every operator hand-roll a bridge".

Two constraints shape the answer.

**The rules that make `/api/v1` safe are not in the controllers.** Published-only
reads, soft-deleted rows staying invisible, an ungranted content type being
indistinguishable from an unknown one, relations that may not cross locales,
validation deferred to publish time, revision numbering under a per-entry
advisory lock, the transactional outbox, i18n sibling sync. They live in
`PublicEntriesQuery`, `PublicEntryWritesService`, and `EntryWriterService`
beneath them. A second entry point that re-implemented any of it would not be a
second entry point; it would be a second, quietly diverging security model.

**We will want tools for our own copilot too.** Its design already anticipates a
tool registry and a `COPILOT_TOOL_PROVIDER` port. Building an MCP-shaped tool set
now and a copilot-shaped one later means two catalogues, two authorization
paths, and two places to add every future capability.

## Decision

**1. Expose the CMS as an MCP server, as a plugin, over a shared tool registry.**

A new `@orthacms/mcp-server` plugin owns the protocol and nothing else: the
Streamable HTTP endpoint at `POST /api/v1/mcp`, bearer authentication, workspace
resolution, and JSON-RPC dispatch. It contains no content knowledge.

**2. The tool contract is transport-neutral, and the registry has two consumers.**

`ToolDefinition` / `ToolContext` / `ToolRegistry` mention no HTTP, no JSON-RPC,
and no MCP. The MCP endpoint is one adapter over the registry; the copilot's
in-process tool loop will be the other, injecting the same instance. A tool added
for either is automatically available to both, and neither can acquire a private
set of rules. This is why the registry lives in the MCP package but is named for
tools rather than for the protocol.

**3. Capability plugins contribute tools; the MCP package never learns about them.**

`content/server` implements `ToolProvider` and registers itself with the registry
it injects `@Optional()`. The inversion is what lets a tool handler call
`PublicEntriesQuery` and `PublicEntryWritesService` **directly** — they are
internal to content and are not, and should not be, exported for an outside
package to drive. Adding media or user tools later is a provider in that plugin
and no change here.

**4. Tools are generic, with `typeName` as an argument.**

Twelve tools, flat, whatever the content model — not a generated set per content
type. An MCP client loads every tool schema into the model's context on connect,
so `article_create`, `author_create`, `tag_create`… would scale the prompt cost
of every conversation with the number of collections, and could not be a fixed
set anyway (visible types depend on the token's workspace grants). Models
discover a shape on demand with `content_type_get`, generated by the same
`docs/field-schema.ts` that produces the OpenAPI document.

**5. The same credential, the same rules, one enforcement point.**

MCP takes the existing bearer API tokens, verified through the same
`ApiTokenService.verify`, with permissions derived by the same
`scopePermissions`. Revoking a token revokes its MCP access in the same instant,
and there is no second credential store.

Because Nest gates _routes_ and MCP is one route carrying many operations, the
per-route `@RequirePermissions(...)` becomes a declared `requires` on each tool,
enforced centrally by `ToolRegistry.call` **before dispatch**. `tools/list`
filtering is a usability nicety — a client may invoke a name it was never shown
— so the check in `call` is the security boundary and must stay that way.

**6. A session cookie is not accepted, exactly as on `/api/v1`.**

Cookies ride along ambiently, which is what makes cookie-authenticated writes
CSRF-able. Accepting them on an endpoint whose purpose is letting an agent write
content would reintroduce that for no gain — every MCP client can send a header.

**7. Stateless, and off by default.**

No session store, no sticky routing; the endpoint scales like the rest of
`/api/v1`, and the per-request protocol server is what lets the tool list reflect
the caller's scope. `MCP_ENABLED` gates it, defaulting to off for the same reason
as the copilot's kill switch (ADR-0005 §10): handing an external agent content
CRUD is a decision an operator makes deliberately, not one they inherit from an
upgrade.

## Consequences

**Good.**

- One implementation of every content rule, reachable two ways. A change to the
  visibility predicate cannot apply to REST and miss MCP.
- A `read`-scoped token never even sees the write tools, and cannot call them.
- Our copilot inherits a built, tested tool catalogue instead of growing a
  parallel one.
- One new runtime dependency (`@modelcontextprotocol/sdk`), confined to one
  package.

**Costs and risks.**

- **The `requires` declaration is now a security-critical field.** A tool added
  with the wrong permissions is a privilege bug that no type checker catches.
  The registry's authorization tests are the guard, and a new tool needs one.
- **Prompt injection reaches content.** An agent reading a CMS entry that
  contains instructions may act on them. Nothing here can prevent that; what it
  bounds is the blast radius — the token's scope, its workspace bucket, and its
  grants. Operators should mint narrow tokens, and the default-off switch means
  they choose to accept this at all.
- **Writes are attributed to a token, not a person.** Revisions record a _user_
  id, and a token is not a user, so agent-authored revisions carry `null` — the
  same pre-existing gap the public write API has. It wants its own column; that
  is unchanged by this ADR and worth fixing before agent authoring is common.
- **The tool descriptions are a real interface.** They are the only
  documentation a model gets, so workflow rules (create yields a draft, publish
  is separate, update merges) have to live in them and stay accurate.
- **`?workspaceId=` on the endpoint URL** is a second spelling of the
  `X-Workspace-Id` header, added because MCP client configs are URL-shaped. It
  goes through the identical bucket check, but it is one more place that rule is
  spelled.
